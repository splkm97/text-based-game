## 계약

`prototype/remains.json`을 프로토타입의 테마·세계관·인물·사건을 기록하는 기준 원장으로 취급한다. 관련 서사 근거가 필요하면 현재 원고인 `prototype/stories/example.md`를 읽는다. `prototype/remains.md`는 현재 권위 자료가 아니며 참조하거나 새로 만들지 않는다. 이 스킬은 되돌릴 수 있는 로컬 수정만 수행한다. 커밋, 게시, 원격 상태 변경은 수행하지 않는다.

## 모드

요청에서 다음 모드 중 하나를 선택한다.

- `add`: 테마, 설정, 인물 정보, 사건을 추가한다.
- `delete`: 설정과 그 설정을 참조해 고아 참조가 생기는 항목을 삭제한다.
- `modify`: 원문 의미와 정보 공개 범위를 보존하면서 기존 설정을 수정한다.
- `schema`: 새 도메인(예: 엔딩·경로·플래그·정보층)을 추가하거나 기존 도메인의 필드 구조를 바꾼다. 값의 내용은 다루지 않는다 — 값 추가는 `add`가 한다.

모드나 대상이 명확하지 않으면 모호한 내용을 보고하고 수정하지 않는다.

## 절차

1. 수정 전에 `prototype/remains.json`과 관련 `prototype/stories/example.md` 구간을 읽는다. 원고 근거가 필요하지 않은 순수 원장 구조 변경이면 원고 읽기를 생략할 수 있다. 완료 조건: 읽은 파일 목록과, 원고 읽기를 생략했다면 그 사유가 보고에 있다.
2. 대상 모드, JSON 경로, 영향을 받는 항목, 원문 근거를 확인한다. `schema` 모드에서는 새 도메인 이름·필드 구조와 그 도메인을 참조하게 될 기존 항목을 함께 확인한다. 기억에 의존해 대상 경로를 만들지 않는다. 완료 조건: 모드, JSON 경로, 영향 항목, 원문 근거가 각각 확정되어 있고, 확정하지 못한 대상은 `ambiguous-target`으로 분리되어 있다.
3. 기존 JSON 구조와 명명 방식을 유지한다. 한국어 원문의 의미를 보존하고, 인물의 공개 정보와 비밀 정보를 별도 필드로 유지한다. 완료 조건: 기존 최상위 키와 필드 이름이 유지되고, 공개 정보와 비밀 정보가 서로 다른 필드에 있다.
4. 모드별 변경을 적용한다.
   - **add:** 기존 도메인 중 알맞은 위치에 추가한다. 원문 또는 요청에 명시된 근거가 있는 정보만 추가한다.
   - **delete:** 다른 항목에서 대상에 대한 모든 참조를 찾아 대상과 함께 제거한다. 고아 식별자, 이름, 경로를 남기지 않는다.
   - **modify:** 기존 문장과 새 문장을 원문과 대조한다. 요청이 명시적으로 변경하지 않는 한 확정된 시점, 인과관계, 지식 범위, 공개·비공개 상태를 보존한다.
   - **schema:** 새 도메인은 기존 최상위 키 옆에 같은 명명 방식으로 넣고, 기존 도메인의 필드 구조를 바꿀 때는 그 도메인을 참조하는 모든 위치를 함께 고친다. 구조만 만들고 값은 비워 두거나 `add`가 채운다. 새 도메인이 참조할 기존 항목의 키가 실제로 존재하는지 먼저 확인한다.
   완료 조건: 적용한 변경마다 JSON 경로와 근거가 있고, 근거 없는 항목이 추가되지 않았으며, 삭제·수정 후 남은 참조가 없다.
5. 변경한 모든 원장 경로를 확인한다. 원장에 기록된 파일 경로는 저장소에 실제로 존재해야 한다. 완료 조건: 원장에 기록된 모든 경로가 저장소에 존재하거나, 해결하지 못한 경로가 `missing-path`로 보고에 열거되어 있다.
6. 모든 명령을 Node 24 환경에서 실행한다. `prototype/remains.json`을 파싱하고 변경 필드, 삭제한 참조, 필요한 파일 경로를 확인한다. 파싱 성공만으로 완료 처리하지 않는다. 완료 조건: 파싱, 변경 필드, 삭제 참조, 경로 확인 결과가 각각 보고에 있다.
7. `pnpm verify && pnpm build`를 실행한다. 두 명령은 경고 없이 통과해야 하며, 어느 하나라도 실패하거나 경고를 출력하면 완료 처리하지 않는다. 완료 조건: 두 명령의 통과 여부와 경고 출력 유무가 보고에 있고, 실패·경고가 있으면 `verify-failed`로 처리되어 있다.
8. 모드, 변경한 JSON 경로, 원문 의미 보존 여부, 참조·경로 확인 결과, 정확한 검증 결과를 보고한다. 완료 조건: 다섯 보고 항목과 완료 판정 어휘가 모두 있다.

## 출력 계약

- 산출물: `prototype/remains.json` 한 파일을 제자리에서 수정한다. 이 스킬은 `.outline/` 산출물이나 별도 보고 파일을 만들지 않는다.
- 보고 항목 다섯 개: 모드, 변경한 JSON 경로 목록, 원문 의미 보존 여부, 참조·경로 확인 결과, `pnpm verify && pnpm build`의 정확한 결과.
- 완료 판정 어휘는 `완료|미완료|blocked`만 쓴다. 검증이 경고 없이 통과하지 않았으면 `완료`를 쓰지 않는다.
- `blocked`면 파일을 수정하지 않았거나 `invalid-json`·`meaning-drift`로 이전 내용으로 복구한 상태를 밝히고, 부족한 입력이나 충돌하는 원문 구절을 돌려준다.

## 실패 처리

- **missing-source-evidence:** 근거가 없는 대상은 수정하지 않고, 근거가 부족한 대상을 보고한다.
- **domain-conflict:** 새 도메인 이름이 기존 최상위 키·필드와 겹친다. 이름을 바꾸거나 사람 결정을 받고, 겹친 채로 진행하지 않는다.
- **schema-break:** 기존 도메인의 필드 구조 변경이 그 도메인을 참조하는 항목을 깨뜨린다. 이전 내용으로 복구하고 깨진 참조를 보고한다.
- **ambiguous-target:** 수정하지 않고 서로 다른 JSON 경로나 항목을 보고한다.
- **invalid-json:** 이전 파일 내용으로 복구하고 파싱 오류를 보고한다. 완료로 보고하지 않는다.
- **dangling-reference:** 남은 참조를 제거하거나 이전 내용으로 복구한다. 부분 삭제 상태를 남기지 않는다.
- **missing-path:** 저장소가 의도한 경로를 확정할 수 있을 때만 경로를 수정한다. 그렇지 않으면 이전 내용으로 복구하고 해결되지 않은 참조를 보고한다.
- **meaning-drift:** 이전 내용으로 복구하고 변경안과 충돌하는 원문 구절을 보고한다.
- **verify-failed:** `pnpm verify` 또는 `pnpm build`가 실패하거나 경고를 출력한다. 편집을 임의로 되돌리지 않고 실패한 명령과 경고 원문을 보고하며 판정을 `미완료`로 쓴다. 되돌림 여부는 사람이 결정한다.

## 완료 조건

요청한 모드를 적용하고(`schema` 모드에서는 새 도메인이 참조하는 기존 키와 경로가 모두 존재하고), 모든 명령을 Node 24 환경에서 실행하고, JSON 파싱과 변경 필드 확인에 성공하고, 고아 참조가 없고, 원장에 기록한 저장소 경로가 모두 존재하며, `pnpm verify && pnpm build`가 경고 없이 통과하고, 결과를 보고해야 완료다. 관련 없는 프로토타입 설정이나 다른 세계의 규칙으로 범위를 넓히지 않는다.
