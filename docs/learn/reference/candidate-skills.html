후보 스킬 제안서

스토리 분기 게임 시나리오를 끝까지 쓰려면 지금 surface에 없는 것이 셋 있다: 그래프, 그 그래프의 실행 증거, 그리고 엔딩 세트. 무엇을 새로 만들고 무엇을 만들지 말아야 하는지 정리한다.

0. 요약

먼저 볼 것

각 후보가 파이프라인 어디에 앉고 없으면 무엇이 막히는지는 워크플로우 한 장의 「제안 스킬이 앉는 자리」 표에 있다. 이 문서는 그 자리를 채울 근거·출력 계약·검증 방법을 다룬다. 위치 표를 두 곳에 두지 않는다.

2. 신규 스킬 후보

각 후보는 상류 스킬과 같은 계약을 따른다: 정본은 읽기 전용, 산출물은 .outline/<RUN_ID>/, 사실 범주 4개, 판정 어휘 닫힘, 사람이 결정. 아래 "근거"가 저장소 사실이고, "검증"이 그 스킬이 제대로 도는지 아는 방법이다.

P0-1 · story-graph-compiler

항목내용
목적승인된 정본·scene card·원고에서 기계가 검증할 수 있는 이야기 그래프를 컴파일한다. 노드, 엣지, requires, effects, 플래그, 앵커, route 목록. 산문을 만들지 않고 판정하지도 않는다.
트리거경로·엔딩 검수를 시작하려는데 manifest가 없을 때. 새 장면이 승인되어 그래프를 갱신할 때.
사용하지 말아야 할 때그래프 설계는 story-graph-architect. 실행은 route-replay-runner. 구조 진단은 structural-critic.
입력prototype/remains.json, prototype/stories/example.md, 승인된 scene card 모음, 확정 플래그 목록.
절차① 범위와 RUN_ID 확정, 정본 스냅샷 → ② 원고에서 노드 경계(## N. 제목)와 선택지 (S)를 추출 → ③ 각 선택지에 requires·effects 후보를 붙이고, 근거 없는 것을 [HYPOTHESIS]로 표시 → ④ scene card가 있으면 entry_state·exit_state를 노드 상태로 옮김 → ⑤ 모든 노드의 next를 채우고 끊긴 곳을 open-edge로 기록 → ⑥ 앵커(엔딩·엔딩 후일담 위치)와 route 후보를 열거 → ⑦ story-graph.json + routes.json + 사람 보고서를 쓰고 RUN_DIR 반환.
출력 계약RUN_DIR/outputs/graph/story-graph.json(nodes[]: id, scene, file, line, entry_state, exit_state, choices[]{label, requires[], effects[], next}), RUN_DIR/outputs/graph/routes.json(route_id, choices[], terminal), RUN_DIR/outputs/graph/compile-report.md(미해결 간선·근거 없는 플래그·사람 결정 필요 목록).
실패 처리input-blocked(정본 누락), open-edge(next 미정 — 그래프를 내되 보고서에 열거), ungrounded-flag(원장에 없는 플래그를 만들려 함 — [HYPOTHESIS]로 내리고 사람 승인 대기), hash-mismatch.
근거진단 ①·⑥. 검수 스킬이 요구하는 manifest·fingerprint·anchor의 생산자가 없었다 — §8에서 이 스킬이 착륙해 해소됐다.
경계reverse-outliner는 원고를 표로 뽑지만 기계 형식이 아니고 진행 가능성도 계산하지 않는다. 이 스킬은 합성 가능한 형식을 낸다.
검증같은 정본으로 두 번 컴파일하면 같은 파일이 나온다(플래그 순서 정규화). 그래프의 모든 노드·엣지가 파일:줄 또는 scene card ID 근거를 갖는다. 원장에 없는 플래그가 effects에 있으면 실패한다.
나중에엔진이 생기면 이 스킬은 tools/의 빌드 단계 + 테스트로 내려간다. 지금 스킬로 두는 이유는 형식이 아직 고정되지 않았기 때문이다.

P0-2 · route-replay-runner

항목내용
목적story-graph.json을 실행해 route별 runtime evidence를 만든다. 노드 방문 순서, 평가된 guard, 세워진 flag, 도달한 terminal state. 그리고 그래프 자체의 결함(막다른 곳·충족 불가 guard·미설정 플래그 참조)을 보고한다.
트리거ENDING_ROUTE·MULTI_ENDING 검수 직전. 그래프가 바뀐 뒤.
사용하지 말아야 할 때품질 판정은 검수 스킬의 몫. 이 스킬은 판정하지 않는다 — "이 route는 도달했다", "이 guard는 참이 될 수 없다"만 말한다.
입력story-graph.json, routes.json, 그래프 지문(SHA-256), 탐색 한도(최대 경로 수·깊이).
절차① 그래프 로드·스키마 검증 → ② 노드 도달 가능성 계산(진입 노드에서 forward) → ③ 각 route를 결정적으로 순회(선택은 route에 명시된 대로) → ④ 각 단계의 guard 평가 결과와 flag 상태를 기록 → ⑤ 분기별 미탐색 경로를 한도 내에서 열거 → ⑥ 결함 보고(막다른 노드, 참이 될 수 없는 requires, 한 번도 세워지지 않는 flag, terminal 미도달) → ⑦ evidence와 보고서를 RUN_DIR/outputs/replay/에 쓰고 반환.
출력 계약outputs/replay/<ROUTE_ID>.json(steps[]: node, choice, guards[]{expr, value}, flags, terminal), outputs/replay/graph-evidence.md(Reviewed graph SHA-256, 도달성 표, 결함 목록, 미탐색 영역, Status).
실패 처리schema-invalid, unreachable-terminal, unsatisfiable-guard, unset-flag, budget-exhausted(한도 초과 — 미탐색 영역을 명시하고 부분 evidence를 낸다).
근거진단 ②. 검수 계약이 "수동 guard 읽기는 replay proof가 아니다"라고 명시하는 이상, 증거 생산자는 별도로 있어야 한다.
경계게임 엔진이 아니다. 새 콘텐츠를 만들지 않고, 문장을 생성하지 않으며, 점수를 내지 않는다.
검증같은 그래프·같은 route로 두 번 돌리면 같은 evidence가 나온다. 의도적으로 끊은 엣지를 넣으면 unreachable-terminal로 잡힌다. 이 두 개가 통과하면 스킬이 자기 일을 한다.

P1-3 · story-graph-architect

항목내용
목적이야기 그래프의 형태를 설계한다: 분기 축, 수렴점 위치, 브랜치 예산, 노드별 정보 공개, 가드/효과 초안. 패턴 이름(Ashwell)을 명시적으로 고르고 근거를 남긴다.
트리거여러 장면을 관통하는 분기 구조를 정할 때. "이 선택이 어디서 합류하는가"를 정할 때.
전제원장·원고가 정본이어야 한다. 새 설정을 손에 들고 시작하는 경우 먼저 사람 승인과 remains-ledger-maintenance로 원장에 반영한다 — 붙여넣은 텍스트는 어떤 스킬도 읽지 않는다.
사용하지 말아야 할 때장면 하나의 사양은 scene-architect. 후보 사건 발산은 divergent-ideator. 사후 구조 진단은 structural-critic. 그래프 컴파일은 story-graph-compiler.
입력원장, 원고, 승인된 scene card, docs/ideation/ 후보 중 선택된 것, 그리고 브랜치 예산(감당할 수 있는 노드·문장 수).
절차① 범위·RUN_ID → ② 현재 원고에서 실제 노드·선택을 추출(컴파일러 호출 또는 수동) → ③ 후보 패턴 2개 이상을 비용·감각·근거와 함께 제시 → ④ 선택된 패턴에 대해 수렴점 목록과 각 수렴점의 state-tracking 항목을 확정 → ⑤ 분기 축마다 최소 두 갈래의 구별되는 즉시 결과를 명시 → ⑥ 각 노드의 정보 공개 reveal/conceal를 지식 주체와 함께 적음 → ⑦ 예산 초과 지점과 대안(합류 강화·지연 분기)을 보고 → ⑧ 사람 결정 대기 목록과 함께 출력.
출력 계약outputs/graph/<scope>-design.md: 패턴 선택 근거, 수렴점 표(수렴점, 합류 노드, 합류 뒤 달라지는 것, 근거), 분기 축 표, 노드별 정보 공개 표, 예산 계산(Fabulich 계산식 + 노드 수), [HYPOTHESIS] 목록, 사람 결정 필요 목록.
실패 처리budget-exceeded(예산 초과 — 대안과 함께 내고 확정하지 않음), no-state-tracking(합류하는데 합류 뒤 달라지는 것이 없음 → FAIL로 표기), ungrounded-rule(확정되지 않은 세계 규칙 필요 → [HYPOTHESIS]).
근거진단 ①·⑥. 지금 구조는 사후에만 문제로 드러난다 — G05는 이미 존재하는 tree를 검사한다.
경계패턴을 강제하지 않는다. 원고에서 관찰한 구조에 이름을 붙이는 순서를 지킨다.
검증산출 그래프가 story-graph-compiler를 통과한다. 모든 수렴점에 "합류 뒤 달라지는 것"이 근거와 함께 있다. 예산 계산이 노드 수와 맞는다.

P1-4 · ending-set-architect

항목내용
목적채택할 엔딩 세트를 설계한다: 엔딩 ID, 도달 조건, 배타 상태, 6축 종결 목표, 앵커, outcome rules, 에필로그 의무. 한 회차 누적과 재플레이 전용 요소를 처음부터 계산에 넣는다.
트리거엔딩을 몇 개 둘지, 어떤 엔딩이 배타적인지 정할 때. 새 엔딩을 추가할 때.
사용하지 말아야 할 때엔딩 세트 검토는 narrative-multi-ending-integration. 경로 하나의 완결성은 narrative-ending-route-review. 엔딩 본문 산문은 narrative-rewriter.
입력원장(비공개 정보 공개 시점 포함), story-graph.json과 route 목록, 주제 명제 초안, 채택 예정 인물 아크.
절차① 범위·RUN_ID → ② 엔딩 후보를 일반·진·실패·부분으로 분류 → ③ 엔딩마다 도달 조건·배타 상태·앵커 후보를 붙임 → ④ 6축 종결(서사·인물·주제·감정·선택 결과·기억 이미지) 목표를 한 줄씩 적음 → ⑤ 배타성 행렬을 만들어 동시 달성 쌍과 불가능 쌍을 표시 → ⑥ 한 회차가 소비하는 결과 집합을 계산해 재플레이 전용 요소를 표시 → ⑦ outcome rules의 평가 순서를 확정(순서 은닉은 결함) → ⑧ 후보 세트와 사람 결정 대기 목록 출력.
출력 계약outputs/endings/ending-set.md: 엔딩 표(ID·분류·도달 조건·앵커·6축 목표·근거), 배타성 행렬, 한 회차 누적 계산, outcome rules 순서, 에필로그 의무, [HYPOTHESIS], 사람 결정 필요 목록.
실패 처리dominant-route(한 경로가 모든 배타 콘텐츠를 먹음 — 재플레이 동기에서 제외하고 보고), variant-only(제목만 다른 엔딩 쌍 → 병합 또는 분화 요구), unreachable(도달 조건을 만족하는 route가 없음).

3. 신규 스킬이 아니라 기존 소유자 확장이어야 하는 것

대상확장왜 새 스킬이 아닌가
remains-ledger-maintenance schema 모드 신설 — 새 도메인(엔딩·경로·플래그·정보층)을 기존 구조·명명·공개/비밀 분리를 유지한 채 추가하고, 참조 무결성과 pnpm verify && pnpm build를 검증한다. 캐논을 쓰는 스킬이 둘이 되면 "누가 정본인가"가 무너진다. 계약의 단일 쓰기 원칙을 지킨다.
narrative-rewriter draft 입력 추가 — 승인된 scene card(state change: PASS)를 받아 1인칭 초고 블록을 쓴다. 카드가 없거나 FAIL이면 거부한다. 본문을 쓰는 주체가 둘이면 시점·문체 규칙이 두 벌이 된다. 이 에이전트는 이미 0계층 시점 규칙과 1계층 문체 규칙을 자기완결적으로 갖고 있다.
narrative-gate-specialist 출력 경로를 .outline/<RUN_ID>/outputs/reviews/specialists/<GATE>.md로 옮기고, .outline/sdd/plan.md가 없을 때의 처리를 명시한다(Global Constraints 부재를 Limitations에 적고 판정하거나, 계획 파일을 입력으로 요구). 에이전트 하나의 경로·전제 정합 문제다. 스킬을 늘릴 문제가 아니다.
공식 점수 키 18개 primary owner map을 정본 파일(예: .omp/narrative-score-schema.md)로 승격하거나, narrative-report-assembly의 참조를 "정의되지 않은 스키마" 요구에서 실제 문서로 바꾼다. 문서 하나의 부재다. 새 스킬이 아니라 정본 복원이다.

7. 이 제안서를 어떻게 검증할 것인가

  1. P0 두 개만 먼저 만든다. story-graph-compiler가 example.md 2장에서 그래프를 만들고, route-replay-runner가 그 그래프의 route 하나를 재생해 evidence를 낸다.
  2. 그 evidence로 검수 하나를 돌린다. narrative-ending-route-review에 그 evidence를 인라인으로 넣고, mechanics 검사가 UNVERIFIABLE에서 PASS|FAIL로 바뀌는지 본다. 바뀌지 않으면 evidence 형식이 계약과 어긋난 것이다.
  3. 그래프를 일부러 망가뜨린다. 선택지 하나의 next를 없는 노드로 바꾸고 route-replay-runner가 schema-invalid로 잡고 증거를 쓰지 않는지 확인한다. 잡지 못하면 도구가 아니다.
  4. P1은 P0가 안정된 뒤에. 그래프가 없으면 엔딩 설계는 검증할 수 없다.
